Podklad pro samostudium.
    Stav k září 2026 — RHEL 9.6+ a RHEL 10.x.

    Operační systém jako container image

    Image mode pro Red Hat Enterprise Linux

    Image mode je způsob, jak sestavit, distribuovat a aktualizovat Red Hat Enterprise Linux pomocí OCI container image. Operační systém se popíše v souboru Containerfile, sestaví se běžnými container nástroji, uloží se do container registry a server si ho odtud stáhne a nabootuje z něj.

    Tento materiál vysvětluje, jak image mode funguje, čím se liší od dosavadního způsobu správy RHEL, kde dává smysl a co je potřeba promyslet, než se nasadí do produkce. Je psaný k samostudiu — není potřeba nic doinstalovávat ani spouštět, jen číst a procházet interaktivní části.

    Předpokládá běžnou administrátorskou zkušenost s RHEL. Znalost kontejnerů je výhodou, ale není podmínkou; potřebné pojmy jsou vysvětlené průběžně.

    Kapitola 1

    Co je image mode

    Principy, na kterých stojí správa kontejnerů, se uplatní na samotném operačním systému. Technologie, která to umožňuje, se jmenuje bootc — boot container.

    V tradičním nasazení se RHEL nainstaluje z instalačního média a pak se konfiguruje na běžícím stroji — balíčky se doinstalují pomocí dnf, konfigurace se upraví skripty nebo Ansible playbooky. Výsledný stav serveru je součtem instalace a všeho, co se na něm od té doby stalo.

    V image mode se pořadí obrátí. Celý obsah operačního systému včetně aplikací a konfigurace se nejdřív sestaví do jednoho image, ten se otestuje, uloží do registry a teprve pak se nasadí. Server tedy nevzniká konfigurací po instalaci, ale nabootováním hotového, předem sestaveného celku.

    K čemu dochází

    Nejčastější otázka při prvním setkání s image mode zní, jestli operační systém poběží v kontejneru. Neběží. Container image je tady pouze formát balení a přepravy — svou rolí odpovídá ISO obrazu nebo diskovému obrazu virtuálního stroje. Rozdíl je v tom, že se s ním pracuje stejnými nástroji jako s aplikačními kontejnery. Server z něj bootuje nativně: má vlastní kernel, vlastní bootloader, přímý přístup k hardwaru a k firmwaru.

    Vlevo se image sestavuje, vpravo se z něj bootuje. Mezi tím je registry.

    Stejný RHEL, jiný způsob doručení

    Uvnitř bootc image jsou tytéž RPM balíčky, ze kterých se skládá tradiční instalace RHEL. Platí pro ně stejná errata, stejný lifecycle a stejné podmínky podpory. Mění se výhradně způsob, jakým se systém sestavuje a jak se k němu dostanou aktualizace.

    Základní image poskytuje Red Hat na adrese registry.redhat.io/rhel10/rhel-bootc, pro RHEL 9 na registry.redhat.io/rhel9/rhel-bootc. Od aplikačních Universal Base Images se liší tím, že obsahuje i komponenty potřebné ke spuštění stroje — kernel, initrd, bootloader a firmware — které se do aplikačních images tradičně nedávají.

    Plně podporováno od RHEL 9.6 a RHEL 10.0 Součást všech RHEL subskripcí, bez příplatku K dispozici i EUS varianty bootc images

    Image mode běží všude, kde běží RHEL — na bare metalu, ve virtualizaci, v public cloudu i na edge zařízeních. Cílem je jeden společný workflow pro vývojáře i administrátory: Containerfile v Gitu, container registry a CI/CD pipeline, tedy postupy, které většina organizací už používá pro aplikace.

    Kapitola 2

    Package mode a image mode

    Oba režimy jsou plně podporované a mohou vedle sebe běžet v jedné infrastruktuře. Volba se dělá pro konkrétní serverovou roli, ne jednou pro celou firmu.

    Dosavadnímu způsobu správy se nově říká package mode. Nikam nemizí a Red Hat ho podporuje dál. Image mode je druhá možnost, jak tentýž RHEL nasadit. Následující přepínač ukazuje zásadní rozdíl mezi nimi v tom, jak se v čase vyvíjí stav flotily serverů.

    K čemu dochází

    Image mode není náhradou package mode a nemá smysl uvažovat o plošné migraci. Rozhoduje charakter serverové role. Tam, kde je server spíš appliance — plní jednu jasně vymezenou funkci a je jich víc stejných — dává image mode největší smysl. Naopak u strojů s proměnlivým obsahem, které si spravuje několik různých týmů a kde se běžně doinstalovávají balíčky za provozu, je package mode praktičtější.

    Kapitola 3

    Build, deploy, manage

    Životní cyklus systému se rozpadá na tři kroky, které odpovídají tomu, jak se dnes pracuje s aplikačními kontejnery.

    Obsah operačního systému se popíše v souboru Containerfile. Vychází se ze základního rhel-bootc image a přidají se balíčky, konfigurační soubory, agenti a aplikace. Výsledek je textový popis, který lze verzovat, recenzovat v pull requestu a kdykoli znovu sestavit.

    FROM registry.redhat.io/rhel10/rhel-bootc:latest
RUN dnf -y install httpd && dnf clean all
RUN systemctl enable httpd
COPY etc/ /etc/
# V produkci řídí aktualizace management nástroj, ne automatický timer
RUN systemctl disable bootc-fetch-apply-updates.timer

    Sestavuje se běžnými nástroji — Podmanem, na OpenShiftu nebo v libovolné CI/CD pipeline, ať už jde o GitLab CI, GitHub Actions, Tekton nebo Jenkins. Build musí běžet na registrovaném RHEL hostu, případně v CI s předanými entitlementy, aby měl dnf přístup k Red Hat repozitářům.

    podman build -t registry.example.com/os/rhel-web:1.0 .
podman push registry.example.com/os/rhel-web:1.0

    K čemu dochází

    Red Hat přestavuje základní bootc image nejméně jednou měsíčně, u kritických oprav častěji. Nový základní image ale sám o sobě nic nenasadí a nevyvolá přestavbu odvozených images. Kdy se nová verze promítne do vašich serverů, rozhodujete vy tím, že spustíte build a publikujete výsledek.

    Hotový image se dá na cílové stroje dostat několika cestami. Volba závisí na tom, jak se ve vašem prostředí servery dnes provisionují.

    Anaconda a kickstart

    Známý instalátor RHEL. V kickstartu se použije direktiva ostreecontainer s odkazem na image. Funguje s PXE bootem, instalačním ISO i s provisioningem ze Satellite, takže stávající postupy zůstanou v platnosti.

    bootc-image-builder

    Kontejnerizovaný nástroj, který z bootc image vyrobí diskový obraz. Podporované výstupy zahrnují qcow2 pro KVM, vmdk pro vSphere, ami pro AWS, gce, neformátovaný raw a instalační iso.

    bootc install

    Instalace přímo z běžícího kontejneru na disk, ve variantách to-disk a to-filesystem. Hodí se pro bare metal a pokročilé scénáře, kde je potřeba mít plnou kontrolu nad rozdělením disku.

    system-reinstall-bootc

    Převede existující RHEL systém, typicky cloudovou instanci, na image mode. Jde o reinstalaci na stejném stroji, ne o konverzi za běhu.

    Změna systému začíná commitem do Gitu, nikoli přihlášením přes SSH. Pipeline sestaví nový image, uloží ho do registry a servery si ho odtud vyzvednou. Tím se z konfigurace serveru stává artefakt, který má historii, autora a schvalovací proces.

    Příkazy, se kterými se pracuje nejčastěji

    PříkazCo dělá

    K čemu dochází

    Red Hat Satellite od verze 6.17 umí image mode hosty zaregistrovat, zobrazit jejich bootc status a spouštět nad nimi bootc akce přes remote execution. Na stránce Booted Container Images ukazuje, kolik různých digestů ve flotile reálně běží. Rozptyl digestů pod jednou cestou k image je přímou mírou toho, jak moc je flotila rozjetá — a nevyžaduje obcházení jednotlivých serverů.

    Kde je hranice

    Image mode odchylky v konfiguraci výrazně omezuje, protože /usr nelze změnit jinak než nasazením nového image. Neodstraňuje je ale úplně: /etc a /var zůstávají zapisovatelné a ruční zásah do nich je možný. Pravidlo, že všechny změny procházejí přes image, tedy i nadále zůstává věcí procesní disciplíny, ne jen technického opatření.

    Kapitola 4

    Jak to funguje uvnitř

    Tři mechanismy, na kterých image mode stojí: transakční aktualizace s návratem zpět, rozdělení filesystemu na neměnnou a perzistentní část, a slučování konfigurace v /etc.

    Příkaz bootc upgrade stáhne z registry nový image — přenesou se jen vrstvy, které se změnily — a připraví ho vedle běžícího systému jako takzvaný staged deployment. Běžící systém se tím nijak nemění a nová verze se aktivuje až při dalším rebootu.

    Na disku tak souběžně existuje běžící verze, verze, ke které se lze vrátit, a případně připravená nová verze. Nejde o dva pevně rozdělené A/B oddíly: jednotlivé deploymenty sdílejí deduplikované úložiště, takže druhá verze nezabere dvojnásobek místa.

    Následující simulace ukazuje, jak se tyto tři pozice mění při publikaci nového image, aktualizaci, rebootu a návratu zpět. Vyzkoušejte si i kombinaci, kdy je zapnutý automatický timer.

    Akce

    V registry je: v1
    Rollback

    Příkaz bootc rollback přehodí pořadí položek v bootloaderu a zahodí případnou připravenou aktualizaci. Změna se projeví až po rebootu. Předchozí verzi lze vybrat i ručně v menu GRUBu při startu.

    Automatický návrat

    Systém se sám nevrátí zpět jen proto, že nová verze nefunguje. Automatický rollback vyžaduje nakonfigurované health-checky (greenboot), které po startu ověří, že server plní svou funkci. Bez nich je návrat ruční operací.

    Soft reboot

    RHEL 10 umí takzvaný soft reboot — restartuje se jen userspace, kernel a hardware běží dál. Výrazně to zkracuje výpadek, ale je použitelný pouze tehdy, pokud nová verze nemění kernel.

    Na co si dát pozor

    Změny provedené v /etc po aktualizaci se při návratu zpět nepřenesou — obsah /etc se vrátí do stavu, v jakém byl v předchozím deploymentu. Pokud je potřeba nějaký upravený soubor zachovat i po rollbacku, musí se jeho kopie uložit někam pod /var, protože ta rollbackem dotčená není. Druhá past se týká zapnutého timeru: po návratu zpět timer do jedné až tří hodin najde v registry novější verzi a server na ni znovu povýší, pokud se nevypne.

    Root filesystem je v image mode ve výchozím stavu neměnný. Zapisovat lze pouze do /etc a /var; veškerý ostatní obsah pochází z image. Vyberte adresář a zobrazí se, co pro něj platí za běhu a co se s ním stane při aktualizaci.

    K čemu dochází

    Adresář /opt bývá v praxi nejčastějším zdrojem překvapení. Software třetích stran se do něj tradičně instaluje a nezřídka si do svého podadresáře zapisuje i za běhu — logy, cache, stavové soubory. Za běhu je ale /opt read-only, takže takový zápis selže. Řešením je při sestavení image přesměrovat zapisovaná podadresář do /var, buď symbolickým odkazem, nebo přes BindPaths v systemd jednotce dané služby.

    Dočasná změna pro ladění

    Pokud je potřeba na běžícím systému něco rychle vyzkoušet, příkaz bootc usr-overlay vytvoří nad /usr dočasnou zapisovatelnou vrstvu; totéž umí dnf install --transient. Tato vrstva po rebootu zmizí. Je určená k ladění a diagnostice, ne k trvalým změnám — ty patří do image.

    Konfigurace v /etc je perzistentní, ale nový image s sebou nese i vlastní výchozí /etc. Aby se při aktualizaci nepřepsaly lokální úpravy a zároveň se propsaly nové výchozí hodnoty, provádí se takzvaný třícestný merge.

    Základem je nové výchozí /etc z image. Na něj se aplikuje rozdíl mezi současným a předchozím výchozím stavem. Soubor, který jste lokálně změnili, tak zůstane ve vaší podobě; soubor, kterého jste se nedotkli, převezme novou výchozí hodnotu.

    K čemu dochází

    Merge se provádí při vytváření nového deploymentu, tedy při vypínání systému před rebootem, ne při běhu. Díky tomu přežijí aktualizaci věci jako hostname, síťová konfigurace nebo SSH klíče hostitele, aniž by je bylo nutné po každé aktualizaci znovu nastavovat.

    Kapitola 5

    Kde dává image mode smysl

    Scénáře, ve kterých model neměnného, verzovaného operačního systému řeší reálný provozní problém.

    Edge zařízení

    Velké flotily se spravují přes registry a stahují se jen změněné vrstvy, což šetří pásmo na pomalých linkách. Když se aktualizace nepovede, návrat zpět nevyžaduje výjezd technika. Od RHEL 10 image mode nahrazuje dřívější RHEL for Edge postavený na rpm-ostree.

    AI a strojové učení

    Funkční AI stack je křehká kombinace verzí kernelu, ovladačů GPU a frameworků. V image mode se tato kombinace jednou otestuje a nasazuje se jako jeden celek, takže na uzlech nemůže vzniknout rozdílná kombinace verzí. Ovladače třetích stran se integrují přímo v Containerfile.

    AI frameworky
    ovladače GPU
    kernel

    Appliance — jedna aplikace na jeden server

    Operační systém a aplikace tvoří jednu verzovanou jednotku, která se nasazuje i vrací zpět najednou. Aplikační kontejnery lze s OS image svázat (logically nebo physically bound images) a spouštět je jako systemd služby přes Quadlet.

    Container hosty

    Když už tým staví a publikuje aplikační kontejnery, hostitelský operační systém projde stejnou pipeline, stejným skenováním a stejným schvalováním. Odpadá druhá sada nástrojů a postupů pro OS.

    Standardizované a regulované flotily

    Golden image přestává být dokumentem a stává se auditovatelným artefaktem: zahardenovaný při sestavení, podepsaný a s jednoznačným digestem, podle kterého lze kdykoli doložit, co přesně na kterém serveru běží.

    Kapitola 6

    Bezpečnost a compliance

    Bezpečnostní opatření se posouvají z běžícího serveru do procesu sestavení image, kde se dají automatizovat a doložit.

    1
    Základní image a balíčky od Red Hatu

    Základní bootc image i jednotlivé RPM balíčky podepisuje Red Hat. Důvěryhodný řetězec tedy začíná ještě před vaší pipeline.

    2
    Hardening při sestavení

    Nástroj oscap-im z balíku OpenSCAP aplikuje bezpečnostní profil, například CIS, už při sestavení image. Oproti remediaci po instalaci se tím pokryjí i věci, které se na běžícím systému opravují obtížně. Soulad běžícího systému se pak ověřuje nástrojem oscap úplně stejně jako v package mode.

    Režim FIPS lze zapnout při sestavení i při instalaci image

    3
    Podpis a skenování

    Odvozený image podepíšete vlastním klíčem (Podman se sigstore) a podpis se uloží v registry vedle image. Zranitelnosti se skenují stejnými nástroji jako u aplikačních kontejnerů — v CI i průběžně v registry, tedy dřív, než se image dostane na server.

    Kryptografické zapečetění image vlastními Secure Boot klíči — Technology Preview v RHEL 10

    4
    Server přijme jen to, co má podpis

    Hosty lze nastavit tak, aby stahovaly a bootovaly výhradně podepsané image. Nepodepsaný nebo cizí image se na server nedostane.

    5
    Neměnný běh a auditovatelnost

    Read-only /usr výrazně ztěžuje trvalou neautorizovanou změnu systému — každá změna operačního systému má svůj původ v konkrétním image. Na otázku, co přesně na daném serveru běží, existuje jednoznačná odpověď v podobě digestu.

    Souvislost s bezpečností dodavatelského řetězce

    Postupy v této kapitole jsou tytéž, které se používají k zabezpečení dodavatelského řetězce aplikací: podepisování artefaktů, evidence obsahu v podobě SBOM a průběžná analýza zranitelností. Rozdíl je jen v tom, že se tu uplatní na operační systém. Organizace, která už tyto nástroje má zavedené pro aplikace, je může použít i pro OS.

    Kapitola 7

    Než se nasadí do produkce

    Image mode mění provozní zvyklosti. Následující body je dobré projít dřív, než se rozhodne o nasazení — ne proto, že by šlo o překážky, ale proto, že se na ně obvykle naráží až v ostrém provozu.

    Rytmus aktualizací

    Životní cyklus verze vypadá v image mode jinak než dnes. Errata už nejde nasadit přímo; nejdřív se musí promítnout do nového image.

    Tato cesta se dá celá zautomatizovat a je pak rychlejší a průkaznější než ruční záplatování. Vyžaduje ale, aby ji někdo vlastnil a aby existovalo rozhodnutí, jak často se přestavuje a kdo povyšuje verzi ze stage do produkce.

    Kam patří co

    Rozdělení obsahu mezi image, instalaci a perzistentní data je nejdůležitější návrhové rozhodnutí. Chyba v něm se projeví až při první aktualizaci nebo při rollbacku.

    Tajemství a konfigurace konkrétního serveru do image nepatří — image je totiž sdílený všemi servery dané role a uložený v registry.

    Body k promyšlení

    01 Reboot u každé aktualizace

    Nová verze operačního systému se aktivuje rebootem, případně soft rebootem, pokud se nemění kernel. Je potřeba mít údržbová okna a plán, jak se restartují služby v clusteru. Režim download-only umožní stáhnout aktualizaci dopředu a aktivovat ji až v okně.

    02 Automatické aktualizace jsou ve výchozím stavu zapnuté

    Timer bootc-fetch-apply-updates sám stáhne novou verzi, aplikuje ji a server rebootuje. V produkci se doporučuje ho vypnout přímo v Containerfile a rollout řídit centrálně přes Satellite, Ansible Automation Platform nebo CI/CD.

    03 Registry se stává kritickou infrastrukturou

    Bez dostupné registry se nedá aktualizovat ani nasazovat. Je potřeba vyřešit vysokou dostupnost, zrcadlení pro oddělená a air-gapped prostředí, retenci tagů, aby zůstala dostupná verze pro návrat zpět, a distribuci pull secrets na servery.

    04 Image pipeline potřebuje vlastníka

    Je potřeba určit, kdo spravuje Containerfile, jak často se přestavuje — základní image od Red Hatu se obnovuje nejméně jednou měsíčně — jak se nová verze testuje a kdo rozhoduje o povýšení ze stage do produkce.

    05 Software třetích stran je potřeba ověřit

    Agenti pro monitoring, EDR, zálohování nebo správu hardwaru se musí zapéct do image a ověřit, že za běhu nezapisují do /usr nebo /opt. Některé RPM balíčky navíc obsahují scriptlety, které v prostředí image buildu selžou a je potřeba je upravit. Toto bývá nejčastější důvod, proč konkrétní serverová role do image mode zatím nemůže.

    06 Migrace znamená reinstalaci

    Existující server nelze převést na image mode za provozu. Přechod je reinstalací, byť ji lze u cloudových instancí zautomatizovat nástrojem system-reinstall-bootc. Souběžný provoz package mode a image mode serverů je běžný a plně podporovaný stav, ne přechodná fáze.

    07 Mění se náplň práce týmů

    Administrátoři se posouvají od konfigurace jednotlivých strojů ke správě image a pipeline. Ansible neztrácí smysl, ale těžiště se přesouvá od konfigurace operačního systému k orchestraci rolloutu a ověření stavu flotily.

    Jak obvykle vypadá první krok

    Prakticky vyzkoušet image mode jde na jedné serverové roli — typicky na container hostu nebo na aplikaci typu appliance, kde je obsah dobře ohraničený. Celá smyčka se dá projít v řádu dnů: Containerfile, build v existující CI, uložení do vlastní registry, nasazení, aktualizace a návrat zpět. Užitečná měřítka jsou tři: jak dlouho trvá cesta od vydání errata k nasazení, jak konzistentní je výsledná flotila a jak dlouho trvá návrat k předchozí verzi.
